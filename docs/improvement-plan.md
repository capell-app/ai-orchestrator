# AI Orchestrator — Improvement & Growth Plan

> Package: capell-app/ai-orchestrator · Kind: package · Tier: premium · Product group: Capell Commercial · Bundle: commercial · Status: Draft

## 1. Snapshot

`capell-app/ai-orchestrator` is a thin, admin-surface-only orchestration layer: an in-memory module registry (`src/Support/AIOrchestratorModuleRegistry.php`) plus two contracts (`src/Contracts/AIOrchestratorModule.php`, `AIOrchestratorProviderConnector.php`), three `AsObject` Actions (`List`/`Register`/`Run…CapabilityAction` in `src/Actions/`), two Spatie Data objects (`AIOrchestratorCapabilityData`, `AIOrchestratorRunData`), one approval-level enum, and a single bundled integration module for Layout Builder (`src/Integrations/LayoutBuilder/`). It owns no migrations, no settings, no config file, no routes, no models, and no Filament/Livewire UI (`capell.json` → `database.migrations: false`, `settings: []`, `surfaces: ["admin"]`). It requires `capell-app/{admin,core,layout-builder}`; nothing is in `supports[]`. The only real-world consumer found is `translation-manager`, which correctly `supports` this package and registers its own `AIOrchestratorModule`.

Current marketplace `summary` (verbatim): _"AIOrchestrator provides the orchestration layer for Capell AI modules and capability execution."_ Marketplace screenshots wired in manifest: **1** (`docs/assets/marketplace/extension-card.jpg`), even though `docs/screenshots/` holds **6** captured PNGs (light/dark for 3 scenes).

## 2. Improvements (existing functionality)

- **Remove the dead `AIOrchestratorProviderConnector` contract or wire it into the run path** — The contract declares `complete(AIOrchestratorRunData): array` but is implemented by nothing and referenced nowhere (`grep` across all packages returns only the definition file). Meanwhile `RunAIOrchestratorCapabilityAction::handle()` calls `$capability->actionClass::run($run)` directly, so "provider connectors" are pure fiction in the runtime. Either delete it (honest) or make `Run…` resolve a connector and route `complete()` through it. — keeps the public contract surface truthful — `src/Contracts/AIOrchestratorProviderConnector.php`, `src/Actions/RunAIOrchestratorCapabilityAction.php` — S (delete) / L (wire up).

- **Move the Layout Builder integration out of this package (fix dependency inversion)** — `ai-orchestrator` _requires_ `capell-app/layout-builder` and hard-codes `LayoutBuilderAIOrchestratorModule` + `PreviewLayoutBuilderLayoutPlanAction`, which reaches into `Capell\LayoutBuilder\Actions\PreviewLayoutPlanAction` via a string-built class name. `translation-manager` already demonstrates the correct inversion (it `supports` orchestrator and ships its own module). The orchestrator should depend on nothing AI-consuming; Layout Builder should register its module the way Translation Manager does. — removes a hard dep, lets the core ship without Layout Builder, kills the `Arch` guard that exists only to police this leak — `capell.json` (`dependencies.requires`), `src/Integrations/LayoutBuilder/*`, `src/Providers/AIOrchestratorServiceProvider.php:57`, `tests/Arch/AIOrchestratorBoundaryTest.php` — M.

- **Enforce `approvalLevel` instead of carrying it as inert metadata** — `AIOrchestratorApprovalLevel` is set on every capability but never read by `RunAIOrchestratorCapabilityAction`; the run executes regardless of `None`/`Draft`/`Developer`. For a "premium" package whose pitch is "keeping approvals and capability boundaries explicit" (README), this is the core value prop unimplemented. Add a gate in the Run action (e.g. require explicit opt-in/permission to execute non-`Draft`, or return draft-only output). — turns a documented selling point into real behaviour — `src/Actions/RunAIOrchestratorCapabilityAction.php`, `src/Enums/AIOrchestratorApprovalLevel.php` — M.

- **Validate registry input and prevent silent module/capability collisions** — `AIOrchestratorModuleRegistry::register()` does `$this->modules[$module->key()] = $module;` — a second module with the same `key()` silently overwrites the first, and duplicate capability keys within a module are never detected (`capability()` returns the first match). Both the bundled Layout Builder test and the Translation Manager module use distinct keys today, but two consuming packages colliding on a key would clobber each other with no error. Throw on duplicate registration (or namespace capability keys by module). — protects the multi-package extension story that is this package's reason to exist — `src/Support/AIOrchestratorModuleRegistry.php` — S.

- **Make `RunAIOrchestratorCapabilityAction` resilient to a missing/invalid `actionClass`** — It blindly calls `$capability->actionClass::run($run)`. `AIOrchestratorCapabilityData::$actionClass` is typed `string` (only a `@param class-string` docblock), so a typo or uninstalled action surfaces as a raw `Error: class not found` rather than a domain exception. The sibling `PreviewLayoutBuilderLayoutPlanAction` already models the right pattern (`throw_if(! class_exists(...) || ! method_exists(..., 'run'), RuntimeException::class, …)`); apply the same guard centrally. — predictable failures for consumers — `src/Actions/RunAIOrchestratorCapabilityAction.php`, `src/Data/AIOrchestratorCapabilityData.php` — S.

- **Wire the 6 captured screenshots into the manifest** — `docs/screenshots/` contains light+dark captures for capability-list, layout-preview, and approval-state scenes, but `capell.json` → `marketplace.screenshots[]` lists only `extension-card.jpg`. The marketplace card is under-selling an already-shot gallery. — free conversion lift, zero code — `capell.json`, `docs/screenshots.json` — S.

- **Reconcile README/overview with actual code** — `README.md` opener claims the package "coordinates AI providers, prompts, **structured requests**" and `overview.md` lists "Contracts for modules and **provider connectors**" — neither provider coordination nor structured requests exist in code. README "At A Glance" also lists Capell deps as only `core` + `admin`, omitting the `layout-builder` requirement that `capell.json`/`composer.json` actually declare. — docs that overstate scope erode trust for a paid first-party package — `README.md`, `docs/overview.md` — S.

## 3. Missing Features (gaps)

Manifest declares `capabilities: ["ai-orchestrator", "ai-orchestrator-admin"]` but the package delivers only a registry + a single bundled module. Measured against AI-platform norms, the orchestration layer is mostly absent:

- **No actual provider abstraction (table-stakes).** Despite the name and the `AIOrchestratorProviderConnector` contract, there is no provider registry, no provider selection, no OpenAI/Prism/Anthropic driver, and no place to configure a default provider. Every "capability" is just a Laravel Action the consuming package wrote — the orchestrator never talks to an LLM. This is the single biggest gap between the marketing ("coordinates AI providers") and the code.
- **No multi-provider failover or retry (table-stakes).** With no provider layer there is nothing to fail over between. A premium orchestrator should offer primary→fallback provider chains and bounded retries on transient errors.
- **No streaming (differentiator).** `AIOrchestratorProviderConnector::complete()` returns `array` — synchronous only. No streamed/token-by-token contract for live admin UX.
- **No cost/token budgeting or rate limiting (table-stakes for paid AI).** Nothing meters tokens, enforces per-tenant spend caps, or rate-limits capability runs. The manifest sets `adminQueryBudget: 40` but no AI-call budget exists.
- **No prompt template management (differentiator).** `AIOrchestratorRunData` carries a raw `prompt` string + freeform `context` array. No reusable/versioned templates, no variable interpolation, no per-capability system prompts.
- **No embeddings/RAG primitives (differentiator).** No vector store, retrieval, or embedding capability — a natural premium upsell given Capell already has content (Layout Builder pages, Translation Manager keys) to index.
- **No observability / run history (table-stakes).** `database.migrations: false` and the docs explicitly punt persistence to consumers ("Persistence, if needed, belongs to the package that runs the capability"). There is no run log, no latency/cost/error capture, nothing for Diagnostics to surface. A central orchestrator is the _correct_ owner of cross-package AI telemetry.
- **No real health probe.** `AiOrchestratorHealthCheck` only returns `compatibleCapellApiVersion(): '^4.0'` (identical to the `html-cache` stub). It does not report registered module/capability counts or provider reachability, so Diagnostics can't actually answer "is orchestration healthy?" — contrast `password-policy`'s health check, which exposes a real `securityPosture()` report.
- **Capabilities not gated.** Manifest `permissions: []`; the `ai-orchestrator-admin` capability is declared but no policy/gate enforces who may run a capability.

Differentiator vs table-stakes: provider abstraction, failover, retry, token budgeting, rate limiting, run observability are **table-stakes** for a paid AI orchestrator and are missing. Streaming, prompt templating, and embeddings/RAG are the **differentiators** that would justify the `premium` tier.

## 4. Issues / Risks

- **Dead code in the public contract surface.** `src/Contracts/AIOrchestratorProviderConnector.php` is unreferenced (verified by repo-wide grep). It misleads integrators into thinking a provider pipeline exists. — `src/Contracts/AIOrchestratorProviderConnector.php`.
- **Dependency inversion / unnecessary hard dependency.** `capell.json` `requires: capell-app/layout-builder`, yet Layout Builder does not depend on the orchestrator and the orchestrator string-builds `Capell\LayoutBuilder\Actions\PreviewLayoutPlanAction`. Installing the orchestrator drags in Layout Builder even when a buyer only wants Translation Manager AI. — `capell.json`, `src/Integrations/LayoutBuilder/PreviewLayoutBuilderLayoutPlanAction.php`.
- **Silent overwrite on duplicate keys.** `AIOrchestratorModuleRegistry::register()` overwrites by `key()` with no warning; duplicate capability keys resolve to the first. A real cross-package risk as more consumers register. — `src/Support/AIOrchestratorModuleRegistry.php`.
- **Unhandled missing-action failure.** `RunAIOrchestratorCapabilityAction` calls `actionClass::run()` with no `class_exists`/`method_exists` guard. — `src/Actions/RunAIOrchestratorCapabilityAction.php`.
- **Inert enum cases.** `AIOrchestratorApprovalLevel::Developer` and `::None` are defined but used nowhere in the repo (only `Draft` is ever set); approval level is never enforced. Dead branches imply behaviour that doesn't exist. — `src/Enums/AIOrchestratorApprovalLevel.php`.
- **Test gaps.** No test asserts duplicate-registration behaviour, missing-module/missing-capability `InvalidArgumentException` messages (the throw paths in the registry are untested), unknown-`actionClass` handling, or `RegisterAIOrchestratorModuleAction` being idempotent. `RunAIOrchestratorCapabilityActionTest` covers only the happy path with a fixture. `LayoutBuilderIntegrationCoverageTest` couples the orchestrator's test suite to `Capell\LayoutBuilder\Data\LayoutPlanResultData`, so the orchestrator can't be tested in isolation. — `tests/Feature/RunAIOrchestratorCapabilityActionTest.php`, `tests/Unit/*`.
- **Public-output safety: low current risk, future-sensitive.** `cacheSafety.sensitiveOutput: false` and there is no public/frontend surface today (`surfaces: ["admin"]`), so the Capell rule against leaking admin internals isn't currently exercised. But AI output (prompts, model IDs, capability labels, approval levels) is exactly the kind of admin-internal data that must never reach anonymous render if a frontend capability is ever added — bake anonymous/non-admin safety tests in before any public surface ships.
- **Secrets handling: deferred, undefined.** No provider layer means no API-key handling here yet, but the manifest's `commercial.privateDocsRequested` and "provider connector configuration belongs to the consuming integration" (overview) push secret management onto each consumer with no shared guidance — inconsistent key handling risk as consumers multiply.
- **Performance budgets.** `capell.json` sets `frontendRenderBudgetMs: 0` (correct — no frontend) and `adminQueryBudget: 40`, but there is no AI-latency or AI-cost budget in the manifest despite this being an AI package; `cacheSafety.cacheable: false` is appropriate for non-deterministic output but means repeated identical runs are never deduped.
- **i18n.** Orchestrator's own labels are not externalised: `LayoutBuilderAIOrchestratorModule::label()` returns the hard-coded literal `'LayoutBuilder'`, whereas the `translation-manager` consumer correctly uses `__('capell-translation-manager::package…')`. The orchestrator ships no `resources/lang`. — `src/Integrations/LayoutBuilder/LayoutBuilderAIOrchestratorModule.php`.

## 5. Marketplace & Selling

**Critique.** Marketplace `summary`, manifest `description`, and composer `description` are three near-identical, self-referential strings ("AIOrchestrator provides the orchestration layer for Capell AI modules and capability execution" / "Capell AIOrchestrator orchestration package"). They define the product in terms of itself, name no benefit, and name no buyer. For a `premium` first-party paid package this is the weakest possible positioning — and it currently over-promises ("coordinates AI providers") relative to what ships.

**Improved 1-sentence summary:**

> The shared AI backbone for Capell — one place to register, run, and govern AI capabilities across packages, with built-in approval gating so assisted edits stay reviewable.

**Improved 3–4 sentence description:**

> AI Orchestrator gives Capell a single, vendor-neutral layer for AI-assisted workflows so every package doesn't reinvent prompt, provider, and execution plumbing. Packages register typed capabilities through a clean contract and the orchestrator runs them behind explicit approval levels, keeping AI output as reviewable drafts until an editor approves. It already powers AI translation drafting in Translation Manager and AI layout planning in Layout Builder, and is the foundation other AI extensions build on. Install it once and unlock assisted workflows across your whole site without locking into a single AI vendor.
> _(Note: the "vendor-neutral / providers" language is only honest once §3's provider abstraction lands; until then, lead on the capability-registry + approval-gating story.)_

**Screenshot/media gaps.** Manifest exposes 1 image but 6 captures exist (`docs/screenshots/` — capability list, layout preview, approval state, each light+dark). Wire all three scenes into `marketplace.screenshots[]`. Add a short architecture/flow diagram (capability → registry → run → approval) since this is a developer-facing infrastructure package whose value is hard to photograph.

**Pricing/tier/bundle & cross-sell.** Positioned `premium` / `commercial` with `proposedLicense: paid`, `requestedCertification: first-party`, `supportPolicy: priority`. The value play is that it's a **dependency hub**: Translation Manager already `supports` it and the README lists Media AI, SEO Suite, and Agent Bridge as "Best Used With." Because multiple paid packages need it, the strongest commercial model is to bundle the orchestrator into an **AI Extension Suite** (or include it free as the substrate and charge for the capability-providing packages) rather than sell the empty orchestrator standalone — today a buyer who installs only the orchestrator gets the bundled Layout Builder demo and little else. Cross-sell every AI consumer from the orchestrator's listing.

**Differentiators / value props / target buyer.** Differentiators (once built): vendor-neutral provider failover, approval-gated execution, and centralised AI run observability across packages. Value props: stop reinventing AI plumbing per package; keep AI output reviewable; one audit trail for all AI spend. Target buyer: agencies/site owners running multiple Capell AI packages, and developers building AI capabilities on Capell who want a contract instead of bespoke glue.
